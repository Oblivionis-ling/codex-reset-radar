# Codex Reset Radar corpus standard

Current version: `crr-corpus-v1`.

This standard defines one content-centred exchange format for live captures, historical material, Reset
events, review cases, and review results. It does not replace the V2 database with a second storage
system, and it does not make third-party source reputation part of the Radar decision. The canonical
database remains the product store; UTF-8 JSONL packages are deterministic review and interchange
artifacts.

## Package files

| File | Record identity | Purpose |
|---|---|---|
| `posts.jsonl` | `post:x:<tweet_id>` | One canonical post per string Tweet ID |
| `reset_events.jsonl` | `event:<event_key>` | Canonical Full and Special events |
| `review_cases.jsonl` | stable `sample_id` | Existing POST_SEMANTICS, EVENT_RECOGNITION, or JUDGE_WINDOW examples |
| `review_results.jsonl` | stable result ID | GPT reference, product-program result, or human decision |
| `manifest.json` | package ID | Freeze time, source database hash, code/worktree identity, model/Prompt versions, file hashes |

Local review packages may additionally contain baseline/corrected program results, comparisons,
unresolved items, source-evidence extracts, logs, and an isolated replay database. Those are ignored
assets and are not distributed with the public repository.

Every JSONL line is one JSON object encoded as UTF-8. Tweet IDs are strings. Missing information is
`null` or an explicit status; importers must not invent midnight, noon, English originals, authors,
scope, completion, or outcomes.

## Post semantics and database mapping

| Standard field | V2 mapping / rule |
|---|---|
| `stable_id`, `tweet_id` | `post:x:<tweet_id>`, `tibo_posts.tweet_id` |
| `author.handle` | evidence author when unambiguous, otherwise the original URL handle, otherwise `null` |
| `content.original_text` | `original_text`; never generated by translating Chinese back to English |
| `content.original_language` | `original_language` |
| `content.translation_zh` | `translated_text`, kept separate from the source text |
| `content.content_hash/version` | `text_hash`; the hash is the content version when no revision counter exists |
| `time.published_at` | `posted_at`, UTC when known |
| `time.precision/basis` | `time_precision`, `time_source` |
| `relationships` | reply flag and parent Tweet identifiers |
| `completeness` | content, context, and conflict statuses |
| `processing` | analysis/translation state and safe error |
| `review` | review state only; it does not overwrite the product result |

One Tweet ID has one canonical record. Source copies remain optional evidence notes and cannot become
additional samples. A meaningful text conflict remains visible until reviewed. Browser translation,
quoted copies, truncated excerpts, parent IDs without bodies, and mixed-author captures have distinct
statuses.

The collector already enters the same semantic fields through `upsert_posts_detailed`: source text,
language, translation, hash, reply relation, and processing state. The standard importer uses that same
entry boundary in an isolated environment and then restores review-only metadata; it does not bypass the
product pipeline or write answers.

## Reset event semantics

An event records mechanism, scope, execution stage, a time range and basis, evidence Tweet IDs, effects,
and cycle impact. Existing `FULL_RESET`, `SPECIAL_RESET`, and Special subtypes remain the database
contract.

- Incident compensation is a reason, not automatically a Special mechanism.
- Announced, rolling out, completed, delayed, cancelled, and unknown are different stages.
- A Full Reset plus banked credit has two effects and one Full cycle start.
- A Full Reset plus temporary higher quota has one Reset and a non-Reset quota effect.
- “Completed once; another later” contains one completed event and one future relation.
- Announcement post time may be a labelled proxy; it is not an exact completion minute.
- Older history may rebuild old cycles but cannot replace the latest event-time cycle.

## Review objects

Sample purposes are:

- `POST_SEMANTICS`: author, source text, translation, time, negation, condition, and meaning;
- `EVENT_RECOGNITION`: mechanism, stage, scope, multi-effect handling, merge/split, and cycle impact;
- `JUDGE_WINDOW`: an `as_of`-bounded Action Level, horizons, estimate, and evidence set.

Review statuses are `UNREVIEWED`, `GPT_REVIEWED`, `PROGRAM_REVIEWED`, `AGREED`,
`NEEDS_HUMAN_REVIEW`, `HUMAN_DECIDED`, `INSUFFICIENT_INPUT`, and `EXCLUDED`.
GPT, product-program, and human results are separate records. Agreement is not human approval.
`HUMAN_DECIDED` requires a real person, decision time, concise reason, and final value.

### Field-scoped human adjudication

Simple human forms may classify content without deciding every field of a comparison. Keep the original
export and later user clarifications as separate input evidence. A later explicit clarification overrides
the earlier choice only on the named field/post. A `HUMAN_DECIDED` result records `human_decided_fields`,
`review_scope`, and `whole_object_approved`; it is not blanket approval of the GPT reference, program
result, event scope, or forecast horizons.

An export that stamps every row at download time provides an export timestamp, not a per-click decision
time. Record this in `timestamp_basis`. Repeated post/event/window cards remain traceable by `case_id`
but must not become extra independent posts or events. A content-level decision on a Judge card does not
approve its main level or 24/48/72-hour estimates.

Keep Reset relationship, mechanism, and stage independent. A human may identify a reset card while the
source still describes future issuance. Preserve Full + Banked and completed + next-planned effects
separately. A human override of the text's tense remains explicitly human-attributed; do not rewrite the
source or turn an announcement timestamp into a verified completion minute.

### Product multi-effect analysis

Analysis Prompt/validator `v2-post-semantics-8` adds `effects` to the existing analysis JSON (no SQLite schema
change). Each effect retains mechanism, scope, stage, temporal mode, time basis/range and a verbatim
source quote. The top-level primary summary/category remains API-compatible. `RESET_CARD` is normalized
to the existing `BANKED` subtype for new effect records. A non-Reset quota boost can be retained in
analysis without creating a Reset event.

Each effect also labels `claim_kind`: occurrence, planned occurrence, mechanism information, historical
reference, or context required. Mentioning a reset type or recalling previous resets is not proof of a new
event. Mechanism information remains searchable analysis without becoming an issued-card event. Unknown
event time is not silently replaced by the post timestamp; an explicit proxy basis is required.

If all concrete effects explicitly say occurred and completed/rolling out, an incompatible
top-level future-announcement category is normalized to that stage. The original category is
retained as `model_category` with a normalization note. Mixed occurred + planned effects are
not flattened. This uses structured semantics, never Tweet-ID or keyword overrides.

Judge Prompt `v2-reset-judge-4` applies the explicit human rule: the main Action Level and
forecasts concern Full Reset; banked cards are separate information, not a reason on their own
to raise the Full-reset level. This policy does not approve individual historical colours.
The last-Full-plus-seven-days UI reference is not an empirical event schedule and must not
generate ORANGE/RED or an exact estimated window by itself.

Event deduplication must not use a six-hour time bin as event identity. Repeated evidence for
the exact occurrence is idempotent; independently evidenced close events remain distinct.
Cross-post linkage requires an explicit shared event key. Existing IDs/keys are preserved on
startup; initialization does not merge or delete historical events. Full-cycle IDs are also
preserved when reconstructing intervals so earlier judgement references stay meaningful.

The analysis scope enum includes `plus_pro`. An explicit operation covering every Plus and Pro user is
not expanded to `all_paid` and is not downgraded to `PARTIAL` merely because other plans are unmentioned.
Under the recorded human product ruling it can open a Full cycle when the operation is actually rolling
out or completed. Investigation/monitoring stage is separate from the Reset stage; a continuing incident
investigation does not turn an already completed Reset back into rolling-out. Explicit multiplicity such
as “twice” remains multiple effects rather than one collapsed event.

The existing pipeline expands this array once. Future, delayed, cancelled, unknown-stage and undated
claims remain candidates. Only occurred, eligible effects enter canonical events; Special effects never
open Full cycles. Old analyses without an effects array use the single-effect compatibility path, with
the same stage guard. This does not automatically repair already persisted historical events.

Reference results store concise evidence and reasons, not hidden model reasoning. Existing product cases
and pre-existing analyses are marked as exposure. Future outcomes and the tested object’s own answer are
excluded from historical replay context.

## Validation and compatibility

`apps/backend/app/corpus_standard.py` validates, reads, writes, exports, and imports the standard.
Import into a replay database keeps source and translation separate and leaves analysis pending so the
normal task pipeline performs the work. Package manifests hash the database snapshot, worktree, and
each JSONL file. Invalid enum combinations, numeric Tweet IDs, missing event times, and invalid reviewer
identities are rejected.

Schema v5 source/evidence tables remain for rollback and audit compatibility. Product decisions must not
use a source site label as an event type, scope, stage, or Action Level.
