## 4. 代码精简：先找实现，再决定是否新增

### 4.1 先搜索复用点

新增通知代码前，定位现有：

```text
配置加载与项目根目录解析
HTTP 客户端、超时与资源关闭
敏感信息脱敏
UTC 时间处理、JSON 编码
日志轮转与错误记录
持久任务与有限重试
消息/任务去重与状态保存
项目进程身份及启动停止工具
测试 fixture、Mock transport
```

同一语义的公共能力只维护一处；新增适配器调用它，不在每个文件复制一遍。

HTTPX/Requests 或其他库已有合适依赖时优先复用，不同时引入多个 HTTP 栈。Python 和 TypeScript 之间不为消除表面重复而造复杂跨语言共享层。

### 4.2 共享的边界

共享传输、脱敏、配置、状态和测试调度；保留供应商专有鉴权、字段映射、错误码和异步回执解析。

不能做一个“HTTP 200 就成功”的通用函数吞掉各供应商语义。重试只有一个明确负责的层级，避免客户端、Adapter、Dispatcher 各重试三次造成请求倍增。

先处理有两个以上真实调用点、用途相同的重复代码。只有几行相似但语义不同的代码，不为了行数合并。已审参考答案与实际业务算法的独立性必须保留，不能让测试预期调用被测函数制造自证。

### 4.3 禁止过度设计

不增加插件市场、动态模块加载、全能工作流引擎、消息中间件、新微服务、笼统大杂烩 `utils.py`，也不把全部代码塞回一个巨型文件。

不改变分析/翻译/Judge Prompt、内容政策、Reset 合并/周期算法或数据字段含义。确实遇到无关缺陷时记录，不能顺手重开已经结束的语料阶段。

## 8. 邮件保底：独立 SMTP，不走微信供应商

实现：

```text
项目 Backend → 用户已授权邮箱的官方 SMTP → 用户确认的收件邮箱
```

不把 PushPlus/WPush 的邮件转发当作唯一保底，不搭自建邮件服务器。

复用现有配置机制，预留 `SMTP_HOST/PORT/SECURITY/USERNAME/PASSWORD`、发件人和收件人；邮箱实际供应商由用户稍后选择。不得从历史聊天中擅自选择收件人。

TLS 必须校验证书，不降级明文认证。支持中文主题和纯文本正文，拒绝头部换行注入，发件人需要满足邮箱权限。SMTP 阻塞操作不能拖住 FastAPI 主事件循环。

当前阶段用本地 SMTP 测试桩或 Mock 证明：发送构造、超时、认证失败、拒收、TLS 错误、中文编码以及资源关闭正确。不要因为缺邮箱授权码而只留 TODO。

兜底逻辑与后续真实测试复用同一入口：

| 微信结果 | 邮件策略 |
|---|---|
| 明确失败 | 创建一次邮件兜底 |
| 有限等待后仍无法确认 | 邮件标明“微信结果未确认”，允许一次兜底 |
| 供应商结果正常 | 不因为用户没反馈而自动补发 |
| 无可用微信渠道 | 后续用户选择后可用邮件单独发送 |
| 邮件失败 | 有限重试并记状态，不递归发送失败通知 |

使用通知 ID、目标和兜底原因避免重复排队；邮件 Message-ID 可辅助追踪，但不承诺外部系统恰好一次投递。网络超时后原微信和邮件均可能到达，说明这一边界。

本地电脑断电或断网时邮件也无法发送，不宣称这是异地故障备援。

提供一个适合 Windows 的薄入口，例如 `test-notifications.bat`，复用项目 Python 查找与根目录解析，不复制另一套启动框架。不需要新增 Web 管理后台。

最低能力：

```text
查看各渠道准备状态
```

`prepare`、`check`、`preview`、`selftest` 不得触达真实发送接口。模拟失败只改变隔离测试 transport，不能破坏真实 Token、网络或供应商配置。即使真实凭据误进入自测环境，自测也必须被网络隔离/拦截保护。

未配置渠道可以显示并跳过，不能导致整个 Backend 因可选配置缺失而拒绝启动。

工具在注册、测试、生产不同用途间要有明确标记；本轮结束后日常生产通知保持关闭，后台任务不能在等待用户时悄悄发送。

### 每个渠道固定同一种写法

1. **去哪里：** 给当前核实的官网或登录入口，不给聚合教程。
2. **你要做什么：** 按真实可见页面描述扫码/关注/选微信渠道；不能猜测没看到的菜单。
3. **复制什么：** 明确是 Token、SCT SendKey、IYUU 令牌、WPush API Key 还是专属推送地址。
4. **填哪里：** 指定本地文件和字段，示例只用占位符；不能要求把秘密贴回聊天。
5. **怎么发：** 通过已经写好并验证过的统一入口，选择该渠道。不给含真实凭据的 curl。
6. **手机看哪里：** 具体服务号/会话/应用入口；微信渠道与独立 App 必须分清。
7. **如何记录：** 发出时间、微信内是否收到、锁屏通知、正文可见性、链接是否能点开、失败说明。
8. **卡住怎么办：** 常见错误对应简短下一步；需实名/付费/已有企业资格时可以跳过，不能强迫购买。

允许第一屏是一页操作总览，后面按渠道展开。不要固定声称“十分钟一定测完”。

### 后续人工测试场景（本轮只准备）

每个可用渠道优先两条：微信前台时一条、后台/锁屏时一条；准备相同结构、不同测试 ID 的内容。可提供用户确认后 15 秒发送的选项，方便锁屏观察；这不是本轮自动定时任务。

标题和正文开头都保留“测试、非真实 Reset 预警”，兼顾只显示标题的渠道。正文不链接 `127.0.0.1`，可使用公开原帖链接作为链接测试。

指导用户记录测试时手机与电脑微信登录状态、系统通知设置，不要求用户更改全部系统设置后才开始。

按实际免费/试用额度安排测试，Server酱不同微信通道可能共用额度；不能每个子通道都刷满免费条数。付费前停止，选择其他渠道。长期激活有效性不能用两条即时消息冒充验证。

邮件最后测：直接发送一封，确认收件箱/垃圾箱和中文，再用测试入口模拟微信失败触发邮件。真实模拟兜底也需要当次用户确认。

提供简单结果表，不要求用户读取 JSON：

| 渠道 | 前台收到 | 锁屏弹通知 | 正文可读 | 大致延迟 | 使用是否麻烦 | 备注 |
|---|---|---|---|---|---|---|

用户只需填写自己的观察，API 结果、消息 ID、错误码由程序自动整理。

## 11. 离线验收与非退化检查

真实发送留到用户参与阶段；准备阶段用离线测试验证：

- 所有第一组 Adapter 的请求构造和业务响应解析；
- HTTP 200 但业务失败、异步 pending、回执未知；
- 配置缺失、凭据脱敏、长度与中文格式；
- 超时、有限重试及重复兜底防护；
- SMTP 构造/TLS/认证/拒收/关闭资源；
- 某个可选渠道未配置不影响其他组件；
- 任何 check/preview/selftest/startup 都不会真实发送；
- 本轮未启用日常通知、历史重放和任务完成提醒；
- 代码精简没有改变采集、内容政策、Reset 周期、Judge 和 API 契约。

使用 Mock 的测试结果必须标记 `OFFLINE_PASS`，不能填 `DELIVERED`。

运行当前 Backend、Web、Collector 测试、类型检查、构建和必要启动 smoke；检查文档链接、移动后的 import/脚本路径与源码依赖。按实际执行统计，不用旧测试数量凑结果。

有必要加载新代码时安全重启项目进程，确认没有重复监听，保持采集和前端可用。生产新帖子自然进入可以改变数量，但测试不能插入假业务事件或触发额外模型重判。

## 12. Git 与变更管理

在独立工作分支进行，清理/复用与通知准备分开形成可审查的改动组；允许建立本地检查点提交，便于恢复。
